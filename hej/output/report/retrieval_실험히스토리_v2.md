### 파이프라인 설계

처음 구현한 파이프라인은 6단계 하이브리드 검색 구조.


## 2. 1차 수정 — 데이터 모수 정합성 + Soft Boost 산식 (v1 → v3)

### 문제 1: ChromaDB 문서 누락

ChromaDB에 3,743개만 인덱싱된 것이 팀원 교차 검증에서 발견. BM25는 10,127개 전체 대상인데 Dense는 3,743개만 보고 있었던 것. 모수 불일치 상태에서 나온 v1 지표는 신뢰 불가.

**원인**: CELL 0의 `CHROMA_EXIST` 판단 로직이 폴더 존재 여부만 체크. 기존 3,743개짜리 컬렉션이 그대로 로드된 것.

**조치**: CELL 4에서 `list_collections()`로 실제 컬렉션 존재 재확인 → `delete_collection` 강제 초기화 → 10,127개 전체 재인덱싱.

### 문제 2: Soft Boost 덧셈 산식의 스케일링 오류

RRF 최대값 약 0.032인데 Soft Boost 덧셈 +0.15가 RRF 점수를 압도. 질문과 무관한 문서도 표/수치 포함 시 최상위 점거.

**조치**: 덧셈 → 곱셈(Multiplier) 전환.

```python
# 수정 전
boosted.append((cid, score + min(boost, SOFT_BOOST_MAX)))

# 수정 후
multiplier = 1.0
if meta.get('has_table',  False): multiplier += 0.10
if meta.get('has_number', False): multiplier += 0.05
boosted.append((cid, score * multiplier))
```

### 문제 3: nDCG > 1 버그

gt 여러 개일 때 동일 gt에 여러 번 매칭되는 버그. DCG가 IDCG보다 커져 nDCG > 1 발생.

**조치**: 1:1 매칭 강제. 매칭된 gt는 `remaining`에서 제거해 재사용 불가 처리.

```python
def _match_flags(gt_stems, retrieved_stems):
    remaining = list(gt_stems)
    flags = []
    for r in retrieved_stems:
        matched = False
        for gt in remaining:
            if gt in r or r in gt:
                flags.append(1)
                remaining.remove(gt)
                matched = True
                break
        if not matched:
            flags.append(0)
    return flags
```

**v3 결과 (공식 베이스라인 확정)**

| 지표 | v1 (오염) | v3 (수정) | Delta |
|---|---|---|---|
| Hit@5 | 0.8509 | **0.8855** | +3.46%p |
| MRR | 0.7298 | **0.8150** | +0.085 |
| nDCG | 1.46 (비정상) | **0.7816** | 정상화 |

## 4. Phase 2 — 쿼리 분해 실험 (v4~v7)

### 배경

v3 기준 B타입(멀티 문서) nDCG 0.6091로 전 타입 최하위. LLM 없이 Retrieval 단에서 쿼리 분해 실험.

---

### 실험 1: 접속조사 기반 구문 분석 (v4, v5) — 실패

Kiwi로 접속조사(JC: 과/와) / 반점(SP)을 Pivot으로 분할. B타입 FAIL 케이스 전수 확인 결과 `sub_queries: N/A` 전부. 실제 B타입 질문이 반점 나열, 괄호 포함, 소유격 혼재 구조여서 pivot 미탐지. 구문 분석 방식 폐기.

실제 B타입 질문 예시:
```
"한국가스공사, 부산국제영화제, 나노종합기술원 세 곳의 IT 기술 사업에서..."
"그랜드코리아레저(주)의 그룹웨어 시스템 구축 예산과 한국원자력연구원의..."
"고려대학교(112억), 코이카(67억), 아시아물위원회(50억)의 3개 사업은..."
```

---

### 실험 2: Agency 사전 매칭 기반 (v6) — 부분 성공

`ALL_AGENCIES` 직접 매칭으로 기관명 추출. 초기 구현에서 형태소 단위 Set 빼기로 Over-stripping 버그 발생. 기관명(`나노종합기술원`) 토큰 `['나노', '종합', '기술', '원']`이 Set에 들어가 일반 명사 `기술`도 삭제. String-level Subtraction으로 전환했으나 Q2 패턴에서 술어가 섞이는 문제 지속.

---

### 실험 3: 위치 기반 앵커링 + 후위 술어 차용 (v7) — 채택

기관명 등장 위치를 Anchor로 삼아 세그먼트 분할. 각 세그먼트 안의 명사만 해당 기관의 로컬 술어로 매핑.

- **Q1 패턴** `[A, B, C + 공통술어]`: 로컬 명사 없으면 마지막 세그먼트 공통 술어 차용 (Borrowing)
- **Q2 패턴** `[A+A술어, B+B술어]`: 로컬 명사 있으면 자신의 술어 사용

`_multi_retrieve`에서 원본 쿼리를 서브쿼리 맨 앞에 포함해 RRF 우선권 확보.

**v7 결과**

| 지표 | v3 | v7 | Delta |
|---|---|---|---|
| Hit@5 | 0.8855 | **0.8927** | **+0.72%p** |
| MRR | 0.8150 | 0.8073 | -0.008 |
| nDCG | 0.7816 | 0.7659 | -0.016 |
| B Hit@5 | 0.8553 | **0.8810** | **+2.57%p** |
| B nDCG | 0.6091 | 0.5666 | -0.043 |

**nDCG 하락 원인: RRF Crowding 현상**

`[원본 쿼리 + 서브쿼리 1 + 서브쿼리 2]`를 동일 비중으로 검색 후 하나의 풀에 합산 → RRF 수행. 서브쿼리들이 유사 문서를 중복으로 가져와 RRF 가점 누적, 정답 문서 순위를 밀어내는 현상. **v7(쿼리 분해) → RRF Crowding 발생 → MMR로 보정** 은 순차적 인과관계.

## 5. Phase 2 — MMR 도입 (v9) 및 파라미터 튜닝

### 설계 원칙

**① 스코어 스케일 불일치 해소**: RRF Boosted 점수(0.01~0.15)와 코사인 유사도(0~1) 스케일 불일치 → MMR 연산 전 Min-Max Scaling으로 각각 정규화.

**② 벡터 캐싱**: `_dense_search`에서 `include=['embeddings']`로 함께 추출해 `_emb_cache`에 저장. MMR에서 재사용, 추가 DB I/O 없음.

### 알고리즘

```
⑤-1 MMR 그리디 선택
    후보 Top-20 대상
    첫 번째: 관련성 최고 문서 선택
    이후: MMR(d) = λ·rel(d) - (1-λ)·max_sim(d, selected)
    λ=0.6 (관련성 60%, 다양성 40%)
```

### v9 결과

| 지표 | v3 | v7 | v9 | Delta (v3→v9) |
|---|---|---|---|---|
| Hit@5 | 0.8855 | 0.8927 | 0.8727 | -1.28%p |
| MRR | 0.8150 | 0.8073 | **0.8398** | **+2.48%p** |
| nDCG | 0.7816 | 0.7659 | **0.8087** | **+2.71%p** |
| B nDCG | 0.6091 | 0.5666 | **0.7257** | **+11.66%p** |

### Lambda / TOP_N 튜닝 실험

| 버전 | Lambda | TOP_N | Hit@5 | MRR | nDCG | B nDCG |
|---|---|---|---|---|---|---|
| v9 | 0.6 | 20 | 0.8727 | **0.8398** | **0.8087** | **0.7257** |
| v10 | 0.7 | 15 | 0.8691 | 0.8373 | 0.8048 | 0.7138 |
| v11 (Lambda만) | 0.7 | 20 | 0.8691 | 0.8373 | 0.8048 | 0.7138 |

Lambda 올려도 전 지표 소폭 하락. v10과 v11 수치가 동일해 TOP_N 조정 효과 없음 확인. **λ=0.6이 이 데이터셋의 균형점.**

### E타입 하락 원인

E타입 분해 오발동 케이스 전수 확인 결과 **0건**. 쿼리 분해 오발동이 원인이 아님. E타입(오타/약칭)은 검색 상위 문서들의 코사인 유사도가 높아 MMR이 다양성 강제 과정에서 정답 문서를 밀어내는 알고리즘적 Edge case. B타입 nDCG +11.66%p 대비 E타입 -5.13%p는 시스템 전체 최적화 관점에서 수용 가능한 비용.

### Hit@5 하락 해석

Hit@5 -1.28%p는 손해가 아닌 투자. Generation LLM은 컨텍스트 중간의 정답을 무시하는 **Lost in the Middle** 현상이 있음. 정답을 5위에 넣는 것보다 1~2위로 끌어올리는 것(MRR +2.48%p)이 Generation 품질에 직결.

### Phase 2 최종 확정 파라미터

```python
DENSE_K    = 15
SPARSE_K   = 15
RRF_K      = 60
TOP_K      = 5      # Top-k 실험 결과 k=5 Sweet Spot 확정
MMR_LAMBDA = 0.6    # 튜닝 실험 결과 0.6이 최적
MMR_TOP_N  = 20     # TOP_N 축소 효과 없어 20 유지
```

## 6. Top-k 실험 (CELL 14)

한 번의 retrieve로 k=3/5/10을 슬라이싱해 동시 측정.

**v5 Reranker 기준 결과**

| k | Hit@k | MRR | nDCG | B nDCG | 토큰 비용 |
|---|---|---|---|---|---|
| 3 | 0.8764 | 0.8518 | 0.8151 | 0.7092 | x0.6 |
| **5** | **0.8873** | **0.8545** | **0.8251** | **0.7311** | **x1.0** |
| 10 | 0.8882 | 0.8546 | 0.8287 | 0.7429 | x2.0 |

**k=5 확정.**

- **k=3**: 토큰 40% 절감하지만 D타입 Hit 0.8889 → 0.8457로 -4.32%p 급락. D타입(함정 질문)은 LLM이 정답 없음을 판별하려면 충분한 컨텍스트가 필요. k=3으로 줄이면 정보 부족으로 환각 위험 증가.
- **k=10**: Hit +0.09%p, nDCG +0.36%p 상승하지만 토큰 비용 2배. 개선폭이 너무 작아 비용 정당화 불가.

## 7. Phase 3 — Reranker 도입 (v11)

### 설계

MPS(Mac M2) 환경에서 `BAAI/bge-reranker-v2-m3` (2.27GB) 로드 정상 확인. MMR 통과 상위 15개만 Reranker 대상으로 제한. 전체 후보에 돌리면 Latency 수 초 단위 폭증.

```
⑤-1 MMR 재정렬
    │
    ▼
⑥-1 Reranker (bge-reranker-v2-m3)
    Top-15 후보 → Cross-Encoder 정밀 재정렬 → Top-5 컷
    │
    ▼
⑦ Top-5 반환
```

### v11 결과

| 지표 | v3 | v9 (Phase 2) | v11 (Phase 3) | Delta (v3→v11) |
|---|---|---|---|---|
| Hit@5 | 0.8855 | 0.8727 | 0.8773 | -0.82%p |
| MRR | 0.8150 | 0.8398 | **0.8487** | **+3.37%p** |
| nDCG | 0.7816 | 0.8087 | **0.8138** | **+3.22%p** |
| B nDCG | 0.6091 | 0.7257 | 0.7126 | +10.35%p |

**Reranker 단독 효과 (v9 → v11)**

| 지표 | v9 | v11 | Delta |
|---|---|---|---|
| MRR | 0.8398 | **0.8487** | +0.009 |
| nDCG | 0.8087 | **0.8138** | +0.005 |
| B nDCG | 0.7257 | 0.7126 | -0.013 |

MRR·nDCG 소폭 개선. B nDCG 소폭 하락은 Reranker가 단일 문서 관점으로 재정렬하면서 멀티 문서 다양성이 줄어든 케이스로 추정.

### Latency 분석

| 구분 | v9 (MMR까지) | v11 (Reranker 포함) | Delta |
|---|---|---|---|
| 단일 쿼리 평균 | 136.5 ms | 1,131.3 ms | **+8.3배** |
| 복수 쿼리 평균 | 200.7 ms | 958.3 ms | **+4.8배** |
| 전체 평균 | 168.6 ms | 1,044.8 ms | **+6.2배** |
| P95 | 292.8 ms | 1,918.1 ms | +6.5배 |

MPS(Mac M2) 환경에서 Cross-Encoder 연산이 1초 이상 소요. CUDA 환경에서는 100~200ms 수준으로 내려올 것으로 예상. **로컬 기준 운영 버전은 v9 유지. CUDA 환경 재측정 후 Reranker 도입 여부 최종 판단 예정.**

## 9. 현재 상태 및 다음 단계

```
 ├─ ③ Sparse 검색 (원본 + 서브쿼리 Union)

 ├─ ⑤ Soft Boost (곱셈)
 ├─ ⑤-1 MMR 재정렬 (λ=0.6, Top-20)
 ├─ ⑥-1 Reranker (bge-reranker-v2-m3, Top-15)
 └─ ⑦ Top-5 반환
```
