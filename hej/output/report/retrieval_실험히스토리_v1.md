## 1. 초기 구조 (Phase 1 베이스라인)

### 파이프라인 설계

처음 구현한 파이프라인은 6단계 하이브리드 검색 구조다.

```
질문
 ├─ ① 메타데이터 Hard Filter   agency / year 퍼지 매칭 → 후보 사전 축소
 ├─ ② Dense 검색  (k=15)       KURE-v1 임베딩 기반 코사인 유사도
 ├─ ③ Sparse 검색 (k=15)       BM25 + Kiwi 형태소 분석
 ├─ ④ RRF 융합                  Reciprocal Rank Fusion (k=60)
 ├─ ⑤ Soft Boost                has_table +0.10 / has_number +0.05 (덧셈)
 └─ ⑥ Top-5 반환
```

|---|---|
| Hit@5 | 0.8509 (85.09%) |
| MRR | 0.7298 |
| nDCG | 1.46 ← 비정상 |

## 2. 1차 수정 — 데이터 모수 정합성 + Soft Boost 산식 (v1 → v3)

### 문제 1: ChromaDB 문서 누락

팀원 교차 검증에서 ChromaDB에 3,743개만 인덱싱된 것이 발견됐다. BM25는 10,127개 전체를 대상으로 검색하는데 Dense는 3,743개만 보고 있었던 것. Dense와 Sparse의 검색 모수가 불일치한 상태에서 나온 v1 지표는 신뢰할 수 없는 값이었다.

**원인**: CELL 0의 `CHROMA_EXIST` 판단 로직이 폴더 존재 여부만 체크했고, 실제 컬렉션 존재는 확인하지 않았다. 기존에 생성해둔 3,743개짜리 컬렉션이 그대로 로드된 것.

**조치**: CELL 4에서 `list_collections()`로 실제 컬렉션 존재 여부 재확인 후, 기존 컬렉션 `delete_collection`으로 강제 초기화 → 10,127개 전체 재인덱싱.

### 문제 2: Soft Boost 덧셈 산식의 스케일링 오류

⑤ Soft Boost가 RRF 점수에 스칼라 값을 단순 덧셈(+0.15)하고 있었다. RRF 최대값이 약 0.032인데 Soft Boost가 +0.15면 부스트가 RRF 점수를 압도한다. 질문과 전혀 무관한 문서라도 표와 수치가 포함되어 있으면 최상위에 올라오는 역전 현상이 발생했다.

**조치**: 덧셈 → 곱셈(Multiplier)으로 전환.

```python
# 수정 전
boosted.append((cid, score + min(boost, SOFT_BOOST_MAX)))

# 수정 후
multiplier = 1.0
if meta.get('has_table',  False): multiplier += 0.10
if meta.get('has_number', False): multiplier += 0.05
boosted.append((cid, score * multiplier))
```

곱셈으로 바꾸면 RRF 점수 0인 문서는 부스트를 받아도 0이고, 점수가 높은 문서가 추가로 올라가는 올바른 방식으로 동작한다.

### 문제 3: nDCG > 1 버그

초기 `calc_ndcg` 함수에서 gt가 여러 개일 때 동일한 gt에 여러 번 매칭되는 버그가 있었다. gt 1개짜리 질문에서 retrieved 여러 개가 동시에 히트하면 DCG가 IDCG보다 커져 nDCG > 1이 발생했다.

**조치**: 1:1 매칭 강제. 한 번 매칭된 gt는 `remaining_gt`에서 제거해 재사용 불가 처리.

```python
def _match_flags(gt_stems, retrieved_stems):
    remaining = list(gt_stems)
    flags = []
    for r in retrieved_stems:
        matched = False
        for gt in remaining:
            if gt in r or r in gt:
                flags.append(1)
                remaining.remove(gt)  # 매칭된 gt 소진
                matched = True
                break
        if not matched:
            flags.append(0)
    return flags
```

**v3 결과 (공식 베이스라인 확정)**

| 지표 | v1 (오염) | v3 (수정) | Delta |
|---|---|---|---|
| Hit@5 | 0.8509 | **0.8855** | +3.46%p |
| MRR | 0.7298 | **0.8150** | +0.085 |
| nDCG | 1.46 (비정상) | **0.7816** | 정상화 |

## 3. C타입 히스토리 평가 추가 (CELL 12 신설)

### 배경

v3 베이스라인에서 C타입(후속 질문)이 Hit 76.92%로 전 타입 최하위였다. 단, 이 수치는 히스토리 없이 단독 질문으로 평가한 최소 성능(Fallback)이다. 검색기 문제인지, 평가 구조 문제인지 판단이 필요했다.

### 조치

CELL 12 전용 평가 루프 신설. eval CSV의 `history` 컬럼을 파싱해 직전 대화 컨텍스트를 쿼리에 합성 후 `get_context(history=[...])` 인터페이스로 검색.

공개 eval 배치 파일 기준 C타입 129개(히스토리 없는 14개 제외) 평가 수행.

**C타입 히스토리 적용 결과**

| 지표 | 적용 전 (Fallback) | 적용 후 | Delta |
|---|---|---|---|
| Hit@5 | 0.7692 | **0.9225** | **+15.33%p** |
| MRR | 0.6719 | **0.8795** | **+0.208** |
| nDCG | 0.6959 | **0.8904** | **+0.194** |

**해석**: C타입 저성능이 검색기 실패가 아닌 평가 구조상 컨텍스트 부재 문제였음이 수치로 확인됐다. 히스토리 적용 후 C타입은 전 타입 중 A타입(96.7%) 다음 2위 수준.

## 4. Phase 2 — 쿼리 분해 실험 (v4~v7)

### 배경

v3 기준 B타입(멀티 문서)의 nDCG가 0.6091로 전 타입 최하위. 단일 쿼리로 복수 기관 문서를 동시에 커버하는 데 한계가 있어, Retrieval 단에서 LLM 없이 쿼리를 분해하는 방식을 실험했다.

---

### 실험 1: 접속조사 기반 구문 분석 (v4, v5)

**설계**: Kiwi로 접속조사(JC: 과/와) 또는 반점(SP)을 Pivot으로 삼아 질문을 분할. 분기점이 없으면 단일 쿼리 즉시 반환해 A/D/E타입 과분해 방지.

**v4 결과**

| 지표 | v3 | v4 | Delta |
|---|---|---|---|
| Hit@5 | 0.8855 | 0.8736 | **-1.19%p** |
| B Hit@5 | 0.8553 | 0.8039 | **-5.14%p** |
| B nDCG | 0.6091 | 0.5279 | **-0.081** |

**실패 원인 분석**: 실제 B타입 FAIL 케이스를 확인한 결과 `sub_queries: N/A`가 전부였다. 실제 B타입 질문들이 `과/와` 접속조사 패턴이 아닌 반점 나열이나 복잡한 구조를 띠어 `pivot_idx == -1`로 전부 단일 쿼리로 빠진 것.

실제 B타입 질문 예시:
```
"한국가스공사, 부산국제영화제, 나노종합기술원 세 곳의 IT 기술 사업에서..."
"그랜드코리아레저(주)의 그룹웨어 시스템 구축 예산과 한국원자력연구원의..."
"고려대학교(112억), 코이카(67억), 아시아물위원회(50억)의 3개 사업은..."
```

구문 패턴이 `A와 B의 C`가 아니라 나열식, 괄호 포함, 소유격('의') 혼재 구조여서 접속조사 기반 분해가 전혀 작동하지 않았다.

구문 분석 방식은 한국어 자연어의 다양한 패턴을 커버하기에 구조적 한계가 있어 폐기.

---

### 실험 2: Agency 사전 매칭 기반 (v6)

**설계 변경**: 구문 분석 대신 `ALL_AGENCIES` 목록과 직접 매칭해 질문에 등장하는 기관명을 추출. 기관명이 2개 이상 발견되면 서브쿼리로 분해.

초기 구현에서 형태소 단위 Set 빼기로 공통 술어를 추출했는데, 팀원 검토에서 치명적 결함이 발견됐다. 기관명(`나노종합기술원`)을 형태소로 쪼개면 `['나노', '종합', '기술', '원']`이 Set에 들어가고, 질문의 일반 명사 `기술`도 삭제되는 Over-stripping 버그.

**조치**: String-level Subtraction으로 전환. 매칭된 기관명을 문자열 자체에서 통째로 replace 후 남은 순수 문자열을 형태소 분석.

그러나 Q2 패턴(`[A + A술어] + [B + B술어]`)에서 A와 B의 술어가 섞이는 문제가 남았다. 기관명 제거 후 남은 모든 명사를 하나의 공통 술어로 간주하는 구조적 한계.

---

### 실험 3: 위치 기반 앵커링 + 후위 술어 차용 (v7) ← 현재

**설계 변경**: 기관명 등장 위치를 기준점(Anchor)으로 삼아 텍스트를 세그먼트로 분할, 각 세그먼트 안의 명사만 해당 기관의 로컬 술어로 매핑.

두 가지 패턴을 모두 처리:
- **Q1 패턴** `[A, B, C] + [공통 술어]`: 로컬 명사가 없는 기관은 마지막 세그먼트의 공통 술어를 차용 (Borrowing)
- **Q2 패턴** `[A + A술어] + [B + B술어]`: 로컬 명사가 있으면 자신의 술어만 사용

추가로 `_multi_retrieve`에서 원본 쿼리도 서브쿼리 리스트 맨 앞에 포함시켜 RRF 융합 시 원본 쿼리 강점을 살리도록 수정.

**알고리즘 흐름**

```
질문 입력
    │
    ▼
ALL_AGENCIES 사전 매칭 (긴 기관명 우선)
    │
    ├─ 기관 2개 미만 → 원본 쿼리 즉시 반환 (A/C/D/E 타입 방어)
    │
    └─ 기관 2개 이상 → 등장 순서대로 정렬 (Anchor 설정)
                │
                ▼
            텍스트 슬라이싱 (기관명 위치 기준 세그먼트 분할)
                │
                ▼
            세그먼트별 로컬 명사 추출
                │
                ├─ 로컬 명사 없음 → 마지막 세그먼트 공통 술어 차용 (Q1)
                └─ 로컬 명사 있음 → 자신의 술어 사용 (Q2)
                │
                ▼
            [원본 쿼리 + 서브쿼리들] → Dense + Sparse 검색 → RRF 융합
```

**v7 결과**

| 지표 | v3 (베이스라인) | v7 (앵커링) | Delta |
|---|---|---|---|
| Hit@5 | 0.8855 | **0.8927** | **+0.72%p** |
| MRR | 0.8150 | 0.8073 | -0.008 |
| nDCG | 0.7816 | 0.7659 | -0.016 |
| B Hit@5 | 0.8553 | **0.8810** | **+2.57%p** |
| B nDCG | 0.6091 | 0.5666 | -0.043 |

**해석**: B타입 Hit@5가 v3 대비 +2.57%p 상승해 멀티 문서 커버리지 향상 목표 달성. 단, MRR과 nDCG는 v3보다 낮음. B타입 Hit는 올랐는데 nDCG가 하락한 건 정답을 찾긴 하지만 순위가 낮아진 것. 서브쿼리 Union 후 RRF 재융합 시 원본 쿼리 점수가 희석되는 효과로 추정.

## 6. 현재 상태 및 다음 단계

**현재 확정된 구조**

```
질문
 ├─ ① 메타데이터 Hard Filter
 ├─ ①-1 쿼리 분해 (Agency 앵커링)   ← Phase 2 추가
 ├─ ② Dense 검색  (원본 + 서브쿼리 Union)
 ├─ ③ Sparse 검색 (원본 + 서브쿼리 Union)
 ├─ ④ RRF 융합
 ├─ ⑤ Soft Boost (곱셈)
 └─ ⑥ Top-5 반환
```

**남은 과제**

| 항목 | 상태 | 비고 |
|---|---|---|
| MMR | ⬜ Phase 2 진행 중 | B타입 nDCG 추가 개선 목표 |
| Top-k 실험 (k=3/5/10) | ⬜ Phase 2 | 토큰 비용 vs 정확도 트레이드오프 |
| Latency 1차 측정 | ⬜ Phase 2 완료 시점 | Phase 3 Reranker 진입 전 베이스라인 확보 |
| Reranker (bge-reranker-v2-m3) | ⬜ Phase 3 | MRR 전체 향상 목표 |
| Release Gate (Hit@5 ≥ 0.9) | ⬜ | 현재 0.8927, 목표까지 0.73%p |
