## 1. 시스템 구조 — 파이프라인 설계

### 왜 이런 구조를 선택했나

입찰 공고 문서(제안요청서)는 텍스트가 길고, 같은 내용이 다양한 방식으로 표현됩니다. 예를 들어 "한국가스공사 ERP 구축 사업"은 "가스공사", "KOGAS", "차세대 통합정보시스템" 등 여러 표현으로 질문될 수 있습니다.

단순 키워드 검색(BM25)만 쓰면 표현 차이에 취약하고, 임베딩 검색(Dense)만 쓰면 정확한 수치/기관명 매칭에 약합니다. 그래서 두 방식을 합치는 **하이브리드 검색**을 선택했습니다.

### 최종 파이프라인 (Phase 3 기준)

```
질문 입력
 ├─ ① 메타데이터 Hard Filter     agency / year 퍼지 매칭 → 후보 사전 축소
 ├─ ①-1 쿼리 분해               기관명 앵커링으로 멀티 기관 질문 처리
 ├─ ② Dense 검색 (k=15)         KURE-v1 임베딩 기반 코사인 유사도 + 벡터 캐싱
 ├─ ③ Sparse 검색 (k=15)        BM25 + Kiwi 형태소 분석
 ├─ ④ RRF 융합                   Reciprocal Rank Fusion (k=60)
 ├─ ⑤ Soft Boost (곱셈)          has_table ×1.10 / has_number ×1.05
 ├─ ⑤-1 MMR 재정렬              λ=0.6, Top-20 후보 대상
 ├─ ⑥-1 Reranker                bge-reranker-v2-m3, Top-15 → Top-5 컷
 └─ ⑦ Top-5 반환
```

## 2. Phase 1 베이스라인 구축 및 버그 수정

### 초기 구현 (v1)

첫 구현은 6단계 파이프라인이었습니다. 결과는 아래와 같았습니다.

| 지표 | 수치 |
|---|---|
| Hit@5 | 0.8509 |
| MRR | 0.7298 |
| nDCG | **1.46 ← 비정상** |

nDCG가 1을 초과했습니다. 이론적으로 nDCG는 0~1 사이여야 합니다. 버그가 있다는 신호였습니다.

---

### 버그 1: ChromaDB 문서 누락

팀원 교차 검증 중 발견된 문제입니다.

**문제**: ChromaDB에 10,127개 전체가 아닌 3,743개만 인덱싱되어 있었습니다. BM25는 전체 10,127개를 대상으로 검색하는데, Dense 검색은 3,743개만 보고 있었던 것입니다. 두 검색기의 검색 대상이 달라지면서 RRF 결과가 오염되었습니다.

**원인**: 초기 구현에서 ChromaDB 초기화 여부를 폴더 존재 여부로만 판단했습니다. 이전에 3,743개짜리 컬렉션이 남아있었고, 그게 그대로 로드되었습니다.

**해결**: `list_collections()`로 실제 컬렉션 존재를 재확인하고, `delete_collection`으로 강제 초기화 후 10,127개 전체를 재인덱싱했습니다.

---

### 버그 2: Soft Boost 덧셈 산식의 스케일링 오류

**문제**: 표/수치가 포함된 문서에 점수를 더해주는 Soft Boost를 덧셈으로 구현했습니다.

```python
# 수정 전 (잘못된 방식)
boosted.append((cid, score + min(boost, SOFT_BOOST_MAX)))
```

RRF 점수의 최대값은 약 0.032인데, 덧셈 부스트 +0.15가 RRF 점수를 완전히 압도했습니다. 질문과 무관해도 표/수치가 있으면 상위권을 독차지하는 문제가 생겼습니다.

**해결**: 덧셈에서 곱셈(Multiplier)으로 전환했습니다. 곱셈은 RRF 점수에 비례해서 가중치를 주므로, 원래 관련성이 낮은 문서가 부스트로 갑자기 치고 올라오는 현상을 막을 수 있습니다.

```python
# 수정 후 (올바른 방식)
multiplier = 1.0
if meta.get('has_table',  False): multiplier += 0.10
if meta.get('has_number', False): multiplier += 0.05
boosted.append((cid, score * multiplier))
```

### 버그 3: nDCG > 1 버그

**문제**: gt(정답 문서)가 여러 개일 때 동일한 gt에 여러 번 매칭되는 버그가 있었습니다. DCG가 IDCG보다 커져 nDCG가 1을 초과했습니다.

**해결**: 1:1 매칭을 강제했습니다. 한 번 매칭된 gt는 후보 목록에서 제거해 재사용 불가 처리했습니다.

```python
def _match_flags(gt_stems, retrieved_stems):
    remaining = list(gt_stems)
    flags = []
    for r in retrieved_stems:
        matched = False
        for gt in remaining:
            if gt in r or r in gt:
                flags.append(1)
                remaining.remove(gt)  # 매칭된 gt 제거
                matched = True
                break
        if not matched:
            flags.append(0)
    return flags
```

## 3. C타입 히스토리 평가 추가

### 배경

질문 유형별로 성능을 분석했을 때, C타입(후속 질문)의 Hit@5가 76.92%로 압도적 최하위였습니다.

C타입은 이전 대화를 전제로 하는 질문입니다. 예를 들어:
- A타입 질문: "한국가스공사 ERP 구축 예산은?"
- C타입 후속: "그 사업의 납기는?" ← "그 사업"이 무엇인지 히스토리 없이는 알 수 없음

이 낮은 성능이 검색기 자체의 문제인지, 아니면 히스토리 없이 평가하는 구조적 문제인지를 먼저 파악해야 했습니다.

### 해결

C타입 전용 평가 루프를 새로 만들었습니다. eval CSV의 `history` 컬럼을 파싱해서 직전 사용자 발화를 현재 질문 앞에 붙여 검색하는 방식입니다.

```python
prev_user = [h['content'] for h in history if h['role'] == 'user']
effective = f'{prev_user[-1]} {query}' if prev_user else query
```

### 결과

| 지표 | 히스토리 미적용 | 히스토리 적용 | Delta |
|---|---|---|---|
| Hit@5 | 0.7692 | **0.9225** | **+15.33%p** |
| MRR | 0.6719 | **0.8795** | **+0.208** |
| nDCG | 0.6959 | **0.8904** | **+0.194** |

+15%p의 극적인 상승이 나왔습니다. **C타입의 저성능은 검색기 문제가 아니라, 히스토리 없이 평가했기 때문이었습니다.** 히스토리를 반영하면 C타입은 A타입(96.7%) 다음 2위 수준입니다.

이후 C타입 평가는 항상 히스토리를 합성해서 진행합니다.

## 4. Phase 2 — 쿼리 분해 실험

### 배경

v3 기준 B타입(멀티 문서 질문)의 nDCG가 0.6091로 전 타입 최하위였습니다. B타입 질문 예시:

```
"한국가스공사, 부산국제영화제, 나노종합기술원 세 곳의 IT 기술 사업에서..."
"그랜드코리아레저(주)의 그룹웨어 예산과 한국원자력연구원의 선량평가시스템 예산은?"
```

여러 기관을 하나의 질문으로 물어보면, 하나의 쿼리로는 모든 정답 문서를 Top-5 안에 넣기가 어렵습니다. LLM 없이 Retrieval 단에서 해결하는 방법을 탐색했습니다.

---

### 실험 1: 접속조사 기반 구문 분석 (v4, v5) — 실패

Kiwi 형태소 분석기로 접속조사(과/와)나 반점(,)을 기준으로 질문을 분할하는 방식을 시도했습니다.

**실패 이유**: 실제 B타입 질문들은 반점 나열, 괄호 포함, 소유격 혼재 등 복잡한 구조였습니다. Pivot이 탐지되지 않아 분해가 전혀 일어나지 않았습니다.

```
"고려대학교(112억), 코이카(67억), 아시아물위원회(50억)의 3개 사업은..."
→ 괄호 때문에 구문 분석 실패
```

---

### 실험 2: Agency 사전 매칭 기반 (v6) — 부분 성공

기관명 사전(`ALL_AGENCIES`)에서 직접 기관명을 찾아 분리하는 방식을 시도했습니다.

**부분 실패 이유**: 기관명 토큰이 Set에 들어가면서 일반 명사까지 삭제되는 버그가 발생했습니다. 예를 들어 "나노종합기술원"의 토큰 중 "기술"이 일반 명사로도 쓰이는 경우 삭제되는 Over-stripping 문제가 있었습니다.

---

### 실험 3: 위치 기반 앵커링 + 후위 술어 차용 (v7) — 채택

기관명이 등장하는 위치(Anchor)를 기준으로 질문을 세그먼트로 나누고, 각 세그먼트의 명사를 해당 기관의 술어로 매핑하는 방식입니다.

두 가지 패턴을 처리합니다:
- **Q1 패턴** `[A기관, B기관, C기관 + 공통술어]`: 로컬 명사가 없으면 마지막 세그먼트의 공통 술어를 차용(Borrowing)
- **Q2 패턴** `[A기관+A술어, B기관+B술어]`: 로컬 명사가 있으면 자신의 술어 사용

또한 원본 쿼리를 서브쿼리 맨 앞에 포함시켜 RRF에서 우선권을 확보했습니다.

**v7 결과**

| 지표 | v3 | v7 | Delta |
|---|---|---|---|
| Hit@5 | 0.8855 | **0.8927** | +0.72%p |
| MRR | 0.8150 | 0.8073 | -0.008 |
| nDCG | 0.7816 | 0.7659 | -0.016 |
| B Hit@5 | 0.8553 | **0.8810** | **+2.57%p** |
| B nDCG | 0.6091 | 0.5666 | -0.043 |

B타입 Hit@5는 +2.57%p 개선되었으나, 전체 nDCG는 하락했습니다.

**nDCG 하락 원인 분석 — RRF Crowding**

원본 쿼리 + 서브쿼리들을 동일 비중으로 검색하면, 유사한 문서들이 여러 쿼리에서 중복 검색되어 RRF 가점이 누적됩니다. 이 누적 가점이 실제 정답 문서의 순위를 밀어내는 현상입니다. 이를 MMR로 보정하기로 결정했습니다.

## 5. Phase 2 — MMR 도입 및 파라미터 튜닝

### MMR을 도입한 이유

MMR(Maximal Marginal Relevance)은 검색 결과의 **다양성**을 확보하는 알고리즘입니다. 이미 선택된 문서와 너무 유사한 문서는 패널티를 줘서, 다양한 정보를 담은 문서들이 Top-5에 들어오도록 합니다.

RRF Crowding으로 인해 유사 문서들이 상위를 독점하는 문제를 해결하기 위해 도입했습니다.

### 구현 시 고려사항

**① 스코어 스케일 불일치 해소**

RRF Boosted 점수는 0.01~0.15 범위인데, 코사인 유사도는 0~1 범위입니다. 두 점수를 그대로 합산하면 스케일이 달라 MMR 연산이 왜곡됩니다. Min-Max Scaling으로 각각 정규화한 후 합산했습니다.

**② 벡터 캐싱**

Dense 검색 시점에 이미 임베딩 벡터를 받아옵니다(`include=['embeddings']`). 이를 `_emb_cache`에 저장해두면 MMR 연산에서 재사용할 수 있어 추가 DB I/O가 없습니다.

### v9 결과

| 지표 | v3 | v7 | v9 | Delta (v3→v9) |
|---|---|---|---|---|
| Hit@5 | 0.8855 | 0.8927 | 0.8727 | -1.28%p |
| MRR | 0.8150 | 0.8073 | **0.8398** | **+2.48%p** |
| nDCG | 0.7816 | 0.7659 | **0.8087** | **+2.71%p** |
| B nDCG | 0.6091 | 0.5666 | **0.7257** | **+11.66%p** |

### Hit@5 하락을 감수한 이유

Hit@5가 -1.28%p 하락했지만, 이를 손해로 보지 않았습니다.

Generation LLM에는 **Lost in the Middle** 현상이 있습니다. 컨텍스트 중간에 있는 정보를 무시하는 경향입니다. 정답을 5위에 넣는 것보다 1~2위로 끌어올리는 것(MRR +2.48%p)이 실제 Generation 품질에 직접적으로 영향을 줍니다.

### Lambda 튜닝

| 버전 | λ | TOP_N | Hit@5 | MRR | nDCG |
|---|---|---|---|---|---|
| v9 | **0.6** | 20 | 0.8727 | **0.8398** | **0.8087** |
| v10 | 0.7 | 15 | 0.8691 | 0.8373 | 0.8048 |
| v11 (λ만) | 0.7 | 20 | 0.8691 | 0.8373 | 0.8048 |

λ를 올려도 전 지표가 소폭 하락합니다. TOP_N 축소도 효과가 없었습니다. **λ=0.6, TOP_N=20이 이 데이터셋의 최적점**으로 확정했습니다.

### 최종 확정 파라미터

```python
DENSE_K    = 15
SPARSE_K   = 15
RRF_K      = 60
TOP_K      = 5
MMR_LAMBDA = 0.6
MMR_TOP_N  = 20
```

## 6. Top-k 실험

한 번의 retrieve 호출로 k=3, 5, 10을 슬라이싱해 동시에 측정했습니다.

| k | Hit@k | MRR | nDCG | B nDCG | 토큰 비용 |
|---|---|---|---|---|---|
| 3 | 0.8764 | 0.8518 | 0.8151 | 0.7092 | ×0.6 |
| **5** | **0.8873** | **0.8545** | **0.8251** | **0.7311** | **×1.0** |
| 10 | 0.8882 | 0.8546 | 0.8287 | 0.7429 | ×2.0 |

**k=5로 확정한 이유**

- **k=3**: 토큰 40% 절감하지만 D타입(함정 질문) Hit가 -4.32%p 급락합니다. D타입은 LLM이 "정답 없음"을 판단하려면 충분한 컨텍스트가 필요한데, k=3이면 정보가 부족해 환각 위험이 커집니다.
- **k=10**: Hit +0.09%p, nDCG +0.36%p 상승하지만 토큰 비용이 2배입니다. 개선폭 대비 비용이 너무 큽니다.

## 7. Phase 3 — Reranker 도입

### 도입 배경

Dense + BM25 + RRF + MMR까지 거쳐도, 최종 Top-5의 순위가 완벽하지 않을 수 있습니다. Cross-Encoder 기반 Reranker는 query와 document를 쌍으로 입력받아 관련성 점수를 직접 계산하므로, Bi-Encoder(임베딩) 방식보다 정밀합니다.

다만 Reranker는 느립니다. 전체 후보에 적용하면 Latency가 폭증하므로, MMR 통과 상위 15개만 Reranker 대상으로 제한했습니다.

```
MMR Top-20 → Reranker Top-15 → 최종 Top-5 반환
```

### v11 결과

|---|---|---|---|---|
| Hit@5 | 0.8855 | 0.8727 | 0.8773 | -0.82%p |
| MRR | 0.8150 | 0.8398 | **0.8487** | **+3.37%p** |
| nDCG | 0.7816 | 0.8087 | **0.8138** | **+3.22%p** |
| B nDCG | 0.6091 | 0.7257 | 0.7126 | +10.35%p |

Mac M2(MPS) 환경에서 Cross-Encoder가 1초 이상 소요됩니다. GCP CUDA 환경에서는 100~200ms 수준으로 내려올 것으로 예상합니다. **GCP에서 Latency 재측정 후 최종 도입 여부를 확정**하기로 했습니다.

### 주요 인사이트

#### 인사이트 1: 청크 전략이 임베딩 모델보다 성능에 더 큰 영향

임베딩 모델(A-1/A-2/B) 간 Hit@5 차이는 최대 0.015 수준입니다. 반면 청크 전략 변경 시 최대 0.05 이상 차이가 납니다.

**무엇으로 임베딩하느냐보다 어떻게 청킹하느냐가 더 중요합니다.** 아무리 좋은 임베딩 모델을 써도, 청크가 잘못 나뉘어 있으면 정답 문서를 검색할 수 없습니다.

#### 인사이트 2: chunks_all이 전체 eval 1위, C타입에서는 역전

chunks_all(max 300자)이 전체 579개 기준 모든 지표에서 1위입니다. 그러나 C타입 히스토리(히스토리 포함 복합 쿼리)에서는 kh_v3에 역전됩니다.

**이유**: 히스토리를 붙인 복합 쿼리는 길고 다층적인 맥락을 포함합니다. 300자 소형 청크는 그 맥락을 한 청크에 담기 어렵습니다. 600자 kh_v3가 복합 쿼리의 여러 키워드를 한 청크에서 커버할 확률이 더 높습니다.

#### 인사이트 3: 큰 청크일수록 임베딩 모델 선택의 의미가 희석됨

kh_fixed_v1(1,000자, 19,118개)은 A-1/A-2/B 결과가 거의 동일합니다. 청크가 크고 수가 많을수록 BM25 어휘가 풍부해져 Dense 임베딩 검색 결과를 덮어버리는 구조이기 때문입니다.

#### 인사이트 4: parent_text 효과는 Retrieval 지표에 안 잡힘

hybrid_ck(Child-to-Parent Retrieval)는 검색은 child text 기준으로 하되, 컨텍스트 반환은 parent_text를 우선합니다. 그런데 평가 지표가 `source_file` 기준이라 어떤 텍스트를 반환하든 지표에 반영되지 않습니다.

**parent_text 효과는 Generation 품질 평가에서 확인해야 합니다.**

### chunks_all parent_text 버그 발견 및 수정

### `_normalize_chunk` 통합 처리 내용

```python
def _normalize_chunk(c: dict) -> dict:
    # Thomas flat 구조 대응: metadata 키가 없으면 최상위가 곧 메타
    if 'metadata' in c:
        meta = dict(c['metadata'])
    else:
        meta = {k: v for k, v in c.items()
                if k not in ('chunk_id', 'child_id', 'chunk_text', 'text', 'parent_text')}

    # agency 정규화
    if 'agency' not in meta:
        meta['agency'] = meta.get('organization_cleaned', meta.get('organization_raw', '미지정'))

    # source_file 정규화
    if 'source_file' not in meta:
        meta['source_file'] = meta.get('original_name', meta.get('filename', ''))

    # has_table / has_number 기본값
    meta.setdefault('has_table',  False)
    meta.setdefault('has_number', False)

    # Thomas fixed_v3: contains_table → has_table
    if 'has_table' not in meta and 'contains_table' in meta:
        meta['has_table'] = meta.pop('contains_table')

    # parent_text 위치 버그 수정 (chunks_all은 metadata 안에 있음)
    parent_text = c.get('parent_text', '') or meta.get('parent_text', '')
    meta.pop('parent_text', None)  # ChromaDB 메타 오염 방지

    # chunk_id 정규화 (kh_v3는 child_id)
    chunk_id = c.get('chunk_id') or c.get('child_id', '')

    return {
        'chunk_id'   : chunk_id,
        'text'       : c.get('chunk_text', c.get('text', '')),
        'parent_text': parent_text,
        'metadata'   : meta,
    }
```
